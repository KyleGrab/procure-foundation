# ProcureIQ — API Map (v1)

Base path: `/api/v1`. Full schema is auto-generated by FastAPI at `/api/v1/openapi.json` once the backend
runs — this file is the human-readable map of what Phase 1 implements now vs. what's reserved for later
phases, so the route names don't have to change as features land.

## Conventions
- Pagination: `?page=1&page_size=50` (max 200), response envelope `{ "items": [...], "total": N, "page": 1 }`.
- Filtering: `?filter[field]=value`, sorting: `?sort=-created_at`.
- Errors: structured per Section 53 of the spec — `{ "error": { "code", "message", "details", "request_id" } }`.
- Every mutating endpoint requires a permission check resolved in the service layer (`app/core/permissions.py`),
  not just a route decorator — see `security.md`.
- Every response is scoped to `active_org_id` from the token; there is no endpoint that accepts an
  organisation id as a request parameter to select which org's data to return.

## Phase 1 (built now)

```
POST   /auth/register              create user + first organisation
POST   /auth/login                 -> access + refresh token (active_org_id = first membership)
POST   /auth/refresh
POST   /auth/logout
POST   /auth/password-reset/request
POST   /auth/password-reset/confirm
GET    /auth/me                    current user + memberships (org list, no cross-org data)
POST   /auth/switch-org            reissue token with new active_org_id (must be an active membership)

GET    /organisations/current      current org profile
PATCH  /organisations/current      update org profile (permission: admin/owner)

GET    /users                      list users in current org (permission: manage_users)
POST   /users/invite               invite user to current org
PATCH  /users/{id}                 update role/status
DELETE /users/{id}                 remove membership (not the user record)

GET    /health
GET    /health/ready
```

## Phase 4 (price review — flagship — BUILT, written as an addendum spec's "Phase 2")
```
/suppliers                                  GET (list), POST (create)

POST /price-reviews                         create review (supplier, currency, price_basis)
GET  /price-reviews/{id}                    review status/metadata
POST /price-reviews/{id}/files/{file_type}  upload previous|new price list, returns suggested mapping
POST /price-reviews/{id}/mapping            confirm column mapping (never auto-applied)
POST /price-reviews/{id}/match              run the matching pipeline over mapped+validated rows
GET  /price-reviews/{id}/lines              full analysis table
POST /price-reviews/{id}/lines/{line}/match-decision       confirm|choose_different|mark_new|mark_discontinued|ignore
POST /price-reviews/{id}/lines/{line}/quantity              manual annual-quantity entry (ADR-008)
POST /price-reviews/{id}/lines/{line}/decision               accept|challenge|negotiate|investigate|ignore
POST /price-reviews/{id}/lines/{line}/negotiation-target
POST /price-reviews/{id}/lines/{line}/negotiation-outcome
POST /price-reviews/{id}/lines/{line}/opportunity            create an Opportunity from this line
GET  /price-reviews/{id}/summary            supplier-level summary (spec Section 19)
GET  /price-reviews/{id}/export.xlsx        multi-sheet Excel export (spec Section 29)
POST /price-reviews/{id}/negotiation-brief  AI brief (spec Section 26) - see phase2-price-review-plan.md §3
```
Route naming differs slightly from the original placeholder list below (kept for history) - the
placeholder used `/matches` and `/impact` as separate concepts; the built version folds match-review into
`/lines` + per-line `/match-decision`, since that's what the actual match-review screen (spec Section 10)
needed. See `docs/phase2-price-review-plan.md` for the reasoning.

Routes are listed here to lock down naming and phase ownership before code exists — reserved routes are
**not** stubbed as 501s in Phase 1; they simply don't exist in the router yet, so `/docs` reflects what's real.
